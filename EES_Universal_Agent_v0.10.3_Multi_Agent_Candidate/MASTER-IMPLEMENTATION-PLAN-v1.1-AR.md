# Elite Engineering Suite — الخطة التنفيذية الرئيسية v1.1

**القرار:** GO لتنفيذ Pilot محدود فقط؛ NO-GO لإطلاق إنتاجي أو لأي ادعاء بأن جودة الوكلاء مثبتة.  
**خط الأساس:** الحزمة v0.7.6  
**تاريخ إعداد النسخة:** 24 أكتوبر 2026  
**الغرض:** تحويل خطة التحسين إلى مراحل تنفيذ قابلة للقياس، مع مالك ومسؤوليات ومخرجات وشروط دخول وخروج لكل مرحلة، وإيقاف التوسع حتى إثبات صلاحية التشغيل الحقيقي.

## 1. الملخص التنفيذي

تم تحويل ملاحظات المراجعة السابقة إلى خطة تشغيلية محددة. الإصدار v0.7.6 يتضمن بالفعل إصلاحات وأدوات تنفيذية أولية، لكنه لا يثبت حتى الآن جودة مخرجات وكيل حقيقي؛ إذ لم يكتمل تشغيل Provider حقيقي داخل Docker في بيئة هذا البناء.

البيانات التي تم التحقق منها في الحزمة:

- 74 مهارة لديها ملفات `SKILL.md`.
- 74 سجل قدرة في السجل المركزي.
- 222 عقد تقييم.
- 51 fixture مركزيًا و11 مشروع fixture تشغيليًا.
- 51 عقدًا كانت تفتقر إلى `success_criteria` صريحة؛ أُضيفت لها معايير مشتقة من `expected_output` و`automated_checks` الموجودة. أصبح العدد الحالي للحالات التي تفتقر إلى معايير نجاح صريحة صفرًا، ويظل محتوى المعايير بحاجة إلى مراجعة بشرية.
- تم تحديث العدّ المرجعي وREADME إلى 222 بدل 216.
- فحص البنية والتوجيه ناجحان دون تحذيرات في آخر تشغيل مسجل.
- تم إعداد Provider Adapter متوافق مع Chat Completions، وصورة Docker Pilot، وManifest ثابت من 5 مهارات و15 حالة.
- فحص البيئة الحالي محجوب: بيانات اعتماد النموذج، ومعرّف النموذج، وDocker والصورة، وتسعير النموذج غير متاحة في بيئة التحقق الحالية.

**الهدف الفوري ليس تشغيل 222 حالة.** الهدف إثبات مسار كامل على 15 حالة من 5 مهارات، مع تسجيل الأدلة والتكلفة والوقت، ثم مراجعة مستقلة قبل توسيع العينة.

## 2. قواعد القرار غير القابلة للتجاوز

1. لا تُحتسب عملية خرجت برمز نجاح على أنها نجاح دلالي للمهمة.
2. لا يُقبل نجاح معلن من الوكيل دون ملفات مخرجات أو أدلة قابلة للتحقق.
3. حالة `unknown` ليست نجاحًا، ولا يجوز حذفها من مقام حساب نسب النجاح دون الإفصاح عنها.
4. لا يُشغّل كود الوكيل خارج العزل المختار؛ عند غياب Docker أو الصورة، تكون النتيجة `blocked` ولا يوجد fallback غير معزول.
5. لا تُحذف مهارة أو تدمج لمجرد تشابه الاسم أو انخفاض نتيجة عينة صغيرة.
6. لا تُثبت عتبات عامة مثل 95% للتوجيه أو 85% للنجاح الدلالي قبل بيانات Pilot ومراجعة توزيع الحالات.
7. لا تُعرض مفاتيح API في سجلات التشغيل أو حاوية التنفيذ أو الملفات الناتجة.
8. أي اشتباه في تسريب سر أو خروج من العزل أو تعديل fixture محمي يوقف Pilot تلقائيًا.

## 4. مراحل التنفيذ وبوابات القبول

المدد أدناه تقديرات تخطيطية لأيام العمل، وتبدأ بعد توفر المستلزمات. يمكن دمج الأدوار في فريق صغير، لكن لا يجوز أن يكون المراجع المستقل هو مؤلف الناتج الذي يقيمه.

### المرحلة 0 — تثبيت خط الأساس وتصحيح العقود

- **المالك المسؤول:** مسؤول صيانة الحزمة.
- **المدة:** نصف يوم إلى يوم.
- **المستلزمات:** Python، مستودع الحزمة، وصول إلى ملفات JSON وREADME.
- **شرط الدخول:** نسخة v0.7.6 نظيفة وقابلة للقراءة.
- **التنفيذ:** توليد baseline؛ فحص الأرقام الفعلية؛ التحقق من معايير النجاح لكل حالة؛ فحص روابط ملفات الأدلة.
- **مخرج التسليم:** `baseline-v076.json`، تقرير إصلاح العقود، سجل فروقات README.
- **شرط الخروج:** `validate --full` ناجح، التوجيه صفر أخطاء/تحذيرات، أعداد README متزامنة، ولا توجد حالة بمعايير نجاح فارغة.
- **الحالة الحالية:** تم إنجاز هذا المسار في v0.7.6؛ يجب إعادة تشغيله عند إعداد أي إصدار جديد.

### المرحلة 1 — اتصال مزود حقيقي

- **المالك المسؤول:** مهندس بنية الوكلاء.
- **المدة:** نصف يوم إلى يوم.
- **المستلزمات:** مفتاح API محفوظ في متغير بيئة على المضيف، اسم النموذج، عنوان API، سعر الإدخال والإخراج لكل مليون token، ميزانية مصرح بها.
- **شرط الدخول:** المرحلة 0 ناجحة، ومراجعة الكود الخاص بالـAdapter مكتملة.
- **التنفيذ:** مكالمة صغيرة حقيقية؛ تأكيد أن استجابة المزود مطابقة للبروتوكول؛ تسجيل token usage؛ اختبار استجابة غير صالحة؛ التأكد من عدم ظهور السر في السجل.
- **مخرج التسليم:** سجل اتصال منقح من الأسرار، إصدار المزود/النموذج، سعر موثق وتاريخ مراجعته.
- **شرط الخروج:** اتصال ناجح قابل لإعادة الإنتاج، استخدام رموز موثق، وعدم تسجيل أي سر. لا يعتبر الاختبار الوهمي أو المحاكى اتصالًا حقيقيًا.
- **الحالة الحالية:** الكود موجود؛ التشغيل الحقيقي محجوب حتى توفير الاعتمادات والموديل والأسعار.

### المرحلة 2 — بناء وفحص العزل

- **المالك المسؤول:** مسؤول DevSecOps.
- **المدة:** نصف يوم إلى يوم ونصف.
- **التنفيذ المختار للـPilot:** Docker CLI، حاوية لكل استدعاء `run_command`، وصورة `ees-pilot-sandbox:0.7.6`.
- **المستلزمات:** مضيف مؤقت أو قابل للتخلص منه مع Docker daemon، حق بناء الصورة، وحدات 2 CPU وذاكرة 2 GB لكل تنفيذ.
- **الشروط التقنية المطلوبة:** `--network=none`، نظام ملفات root للقراءة فقط، إسقاط القدرات `--cap-drop=ALL`، `no-new-privileges`، UID/GID غير root، سقف PID، CPU وRAM، مجلد عمل واحد قابل للكتابة، وfixture و`SKILL.md` للقراءة فقط، وعدم تركيب Docker socket أو مجلد المنزل أو أي ملف أسرار.
- **اختبارات القبول:** رفض المسارات المطلقة و`..` والروابط الرمزية والكتابة في الملفات المحمية؛ timeout؛ قتل الحاوية وإزالتها؛ إثبات أن المفتاح لا يدخل بيئة الحاوية؛ عدم وجود fallback غير معزول عند غياب الصورة.
- **مخرج التسليم:** تقرير بناء، نسخة الصورة وDigest، ومخرجات probes.
- **شرط الخروج:** إثبات الضوابط على حاوية فعلية، وليس بمجرد فحص نص أمر Docker.
- **الحالة الحالية:** إعداد Docker موجود، لكن لم يمكن تشغيله في بيئة البناء لأن Docker/Podman غير متاحين. لذلك هذه المرحلة لم تجتز التشغيل الحي.

**حدود العزل:** Docker مناسب كبداية Pilot على مضيف مؤقت، لكنه يشارك نواة المضيف. لا يعد عزلًا عالي الضمان لتشغيل شيفرات عدائية على مضيف إنتاجي. يجب تثبيت Digest للصورة وتقييم الحاجة إلى عزل أقوى قبل استخدام إنتاجي.

### المرحلة 3 — Pilot 1: 5 مهارات و15 حالة

- **المالك المسؤول:** قائد التقييم.
- **المدة:** نصف يوم إلى يوم، بعد نجاح المرحلتين 1 و2.
- **المهارات المختارة:**
  1. `api-design-contracts`
  2. `database-engineering`
  3. `frontend-development`
  4. `software-testing`
  5. `devops-and-deployment`
- **العينة:** 3 حالات لكل مهارة، مُثبتة في `reports/pilot-manifest-v076.json`.
- **التنفيذ:** تشغيل كل حالة في مساحة عمل جديدة؛ حفظ المخرجات؛ تسجيل الأمر ورمز خروجه والزمن والـtokens والتكلفة المتوقعة وبصمات الملفات المتغيرة؛ حفظ الفشل والـtimeout صراحة.
- **مخرج التسليم:** `pilot-1-run.json` وملفات الأدلة غير المعدلة وسجل المحاولات.
- **شرط الخروج:** إما نتائج الحالات الخمس عشرة، أو حالة `blocked` مبررة لكل حالة لم تنفذ. لا يجوز تحويل الحالات المحجوبة إلى نجاح.
- **الحالة الحالية:** تم اختبار المشغّل بموائم اصطناعي؛ هذا يثبت خط سير الأدوات فقط، لا كفاءة الوكيل.

### المرحلة 4 — المراجعة المستقلة

- **المالك المسؤول:** قائد التقييم؛ والمُحكّم النهائي مسؤول الإصدار.
- **المدة:** يوم إلى يومين.
- **المراجعون:** مراجِعان مستقلان لكل حالة، بخبرة مناسبة للتخصص؛ يحتفظ النظام بالحكمين الأصليين قبل التحكيم.
- **المعلومات المطلوبة:** مصدر معيار النجاح، إشارة دليل لكل حكم، تبرير مختصر، `pass` أو `fail` أو `unknown` لكل معيار.
- **القياس:** نسبة الاتفاق الخام وCohen’s kappa على مستوى المعايير، مع عدد unknown وتوزيع الأحكام. في عينة صغيرة، تعرض kappa بوصفها وصفية لا حقيقة إحصائية مستقرة.
- **عتبات معايرة Pilot:** اتفاق خام لا يقل عن 80% وKappa لا يقل عن 0.70 كإشارة لبدء تفسير النتائج. هذه عتبات للمراجعة والمعايرة، وليست حد إصدار إنتاجيًا؛ إذا فشل أي منها يعاد تدريب المراجعين وتوضيح rubric ثم تحكيم الحالات.
- **مخرج التسليم:** ملفا حكم مستقلان، تقرير الاتفاق، وسجل تسوية الخلافات.
- **شرط الخروج:** تقييم جميع الحالات والمعايير؛ unknown معلنة؛ لا نجاح مستنتج من تقرير الوكيل وحده.

### المرحلة 5 — تدقيق التداخل وملكية المهارات

- **المالك المسؤول:** مالك التوجيه، بمشاركة خبراء المجالات.
- **المدة:** يوم أولي، ثم يوسع حسب المرشحين.
- **الموجود بالفعل:** حقل `conflicts_with`، بيانات ملكية لكل مهارة، وقائمة مرشحين للتداخل في `reports/skill-overlap-candidates-v076.json`.
- **مهم:** علاقات `conflicts_with` معرفة كاستبعاد حقيقي من التوجيه المشترك في نطاق القرار نفسه. لم تُعتمد أزواج تعارض قسرية دون دليل؛ عدد الأزواج الموثقة حاليًا صفر. التداخل المحتمل ليس تعارضًا بالضرورة.
- **مخرج التسليم:** سجل لكل زوج مرشح، وقرار Keep/Improve/Split/Merge/Hard conflict/Deprecate مع أدلة واختبارات توجيه قبل وبعد.
- **شرط الخروج:** الملكية ومسار التسليم واضحان للمهارات المختبرة، ولا توجد إزالة أو دمج غير قابل للتراجع بقرار آلي.

### المرحلة 6 — قرار Pilot وتحديد نطاق التوسع

- **المالك المسؤول:** مسؤول الإصدار.
- **المدة:** نصف يوم.
- **شرط الدخول:** تقارير المراحل 0–5 وأدلة التشغيل والمراجعة والتكلفة مكتملة.
- **قرار GO:** اجتياز الضوابط الأمنية، قابلية إعادة إنتاج الاختبارات، اكتمال سجلات الحالات، وضوح النتائج والأدلة والتكلفة، ومعالجة اختلاف المراجعين.
- **قرار NO-GO:** أي حادثة أمنية، تسرب أسرار، حالة فشل غير مسجلة، جودة لا يمكن تفسيرها، اتفاق مراجعَين دون العتبة، أو ميزانية غير منضبطة.
- **مخرج التسليم:** تقرير قرار مكتوب وأسباب وقيود وخطة إعادة الاختبار.

### المرحلة 7 — Pilot 2: التوسع إلى 15–20 مهارة

لا تبدأ إلا بعد GO موثق من المرحلة 6. تُختار المهارات اعتمادًا على نتائج Pilot 1 ومخاطر الأعمال، وتضاف حالات لاختبار التوجيه والتسليم بين المهارات والتداخل. يجب أن تشمل العينة حالات فشل متوقعة وتخصصات مختلفة، لا مجرد الحالات الأسهل.

### المرحلة 8 — مراجعة وإصلاح المهارات المرشحة

تعالج فقط المشكلات المثبتة بالأدلة، ولا يعاد تصميم جميع المهارات دفعة واحدة. لكل تغيير: سبب مرتبط بفشل، وصاحب قرار، وحالة اختبار قبل التغيير وبعده، واختبار انحدار للمهارات المجاورة.

### المرحلة 9 — التوسع إلى 74 مهارة و222 عقد تقييم

بعد نجاح Pilot 2 فقط. التنفيذ دفعات ذات حجم محدود، ويفضل ألا تتجاوز 12 مهارة في الدفعة. لا تعتمد كل الدفعات دفعة واحدة: كل دفعة تتطلب نتائج فعلية، ومراجعة، وتكلفة، وتدقيق توجيه.

### المرحلة 10 — اختبارات تكامل ونهاية إلى نهاية

تشمل تغييرات متعددة الملفات، handoffs بين المهارات، قواعد البيانات/الواجهات/البناء حيث تتوفر الأدوات، واختبارات الانحدار. أي اختبار يتطلب خدمة خارج البيئة يجب أن يسجل `blocked` أو `unknown` بدل اختراع نتيجة.

### المرحلة 11 — اختبار الأداء والتكلفة

قياس الزمن، عدد استدعاءات النموذج، input/output tokens، التكلفة المقدرة ومطابقتها للفوترة، معدلات timeout وإعادة المحاولة وتباين النتائج. لا يعتمد تحسين سرعة إذا زاد الخطأ أو قلّ التحقق.

### المرحلة 12 — مراجعة أمان مستقلة

اختبار حدود الملفات، الأسرار، الشبكة، صلاحيات العمليات، سجلات الأدلة، وتنظيف بيئة التشغيل. لا تجرى مراجعة الإنتاج بمجرد نجاح اختبارات وحدات؛ يلزم فحص إعدادات المضيف والصورة والاعتماديات.

### المرحلة 13 — بوابة الإصدار والإنتاج

تتطلب تقرير أداء مُثبتًا، ومراجعة أمنية، ومقارنة baseline، وتكلفة معتمدة، وسجل حالات الفشل، وخطة rollback. قرار الإنتاج مستقل عن نجاح Pilot. لا تطلق المنظومة اعتمادًا على عدد المهارات أو نجاح التحقق البنيوي.

## 5. جدول Milestones المقترح

الجدول مرتبط بتوفر الاعتمادات والبيئة؛ ليس وعدًا زمنيًا ثابتًا.

- **M0 — يوم 1:** تثبيت baseline وإكمال إصلاح العقود ومراجعة التغييرات.
- **M1 — يوم 2:** إثبات الاتصال الحقيقي بالمزود مع ضبط التكلفة.
- **M2 — الأيام 2–3:** بناء صورة Docker وإثبات العزل وprobes الفشل.
- **M3 — الأيام 3–4:** تشغيل 15 حالة أو تصنيفها `blocked` صراحة.
- **M4 — الأيام 4–6:** مراجعتان مستقلتان ومعالجة الخلافات وتحليل التكلفة.
- **M5 — الأيام 6–7:** تقرير قرار GO/NO-GO لـPilot 2.

إذا توقفت المتطلبات الخارجية، يسجل milestone على أنه محجوب مع اسم الاعتماد الناقص والمالك وتاريخ إعادة الفحص. لا تُحسب الأيام المحجوبة كإنجاز.

## 6. الميزانية والتحكم في تكلفة الوكيل

لا توجد ميزانية رقمية صحيحة يمكن تحديدها دون معرفة المزوّد والنموذج وأسعار الإدخال والإخراج. لا يوضع رقم افتراضي على أنه ميزانية فعلية.

قبل كل تشغيل:

1. مالك الميزانية يعتمد سقفًا بالدولار أو عملة متفق عليها.
2. يسجل النموذج وتاريخ الأسعار ومصدرها.
3. تهيأ أسعار الإدخال والإخراج لكل مليون token على متغيرات البيئة.
4. يحدد حد أقصى لاستهلاك token وعدد خطوات الأدوات والمهلة لكل حالة.
5. يرفض المشغل الاستمرار إن كان قياس التكلفة غير متاح أو تجاوز السقف.
6. تحفظ التكلفة المتوقعة منفصلة عن الفاتورة الفعلية؛ تتم المطابقة بعد التشغيل.
7. توقف الإعادات التلقائية المكلفة عند تكرار الخطأ حتى مراجعة السبب.

المطلوب من تقرير Pilot: تكلفة كل حالة، المتوسط والوسيط، مجموع التكلفة، عدد الاستدعاءات، نسبة الحالات التي لم تتوفر تكلفتها، وتقدير منفصل للتوسع. أي تقدير للتوسع يجب أن يوضح الافتراضات ونطاق عدم اليقين.

| Improve | إخفاق متكرر قابل للإصلاح أو ارتفاع unknown مع بقاء نطاق فريد | تعديل محدود ثم إعادة اختبار الحالات المعنية والانحدار |
| Split | مجموعتان مختلفتان من المهام بمخرجات ومعايير مختلفة، ولكل منهما أمثلة | اقتراح فصل مع مالك ومجموعة اختبارات مستقلة |
| Merge | تشابه ≥70% في النطاق/المعايير، وتوافق ≥80% من المراجعين على قابلية الاستبدال، وعدم وجود قدرة فريدة | نموذج دمج تجريبي، واختبار التوجيه قبل حذف الأصل |
| Hard conflict | لا يمكن للمهارتين امتلاك القرار نفسه في المهمة نفسها، ولا توجد حاجة طبيعية لاستدعائهما معًا، ومراجعان يوافقان | تعارض متبادل في `conflicts_with` واختبار أثر التوجيه |
| Deprecate | لا توجد معايير فريدة، والوظيفة مغطاة بالكامل ببديل، والدليل مستمر عبر دورتين مراجعة على الأقل | أرشفة مؤقتة، تحديث المراجع، اختبار الانحدار، موافقة مسؤول الإصدار قبل الإزالة |

مع 3 حالات فقط للمهارة في الأساس، لا تُحذف أو تدمج مهارة بسبب النسبة الخام وحدها. أي مرشح دمج/حذف يحتاج على الأقل ست حالات تمييزية قبل اتخاذ قرار غير سهل التراجع.

## 8. حوكمة المراجعة البشرية

- مراجِعان مستقلان لكل حالة، مع سجل بالخبرة ذات الصلة وتعارض المصالح.
- لا يطلع المراجع الأول على حكم الثاني قبل تثبيت الحكمين.
- يجب أن يحتوي كل حكم على النتيجة، وإشارة الدليل، والتبرير.
- يعلن خام الاتفاق وCohen’s kappa وعدد unknown ونسبة كل فئة.
- الهدف الإرشادي في Pilot: 80% اتفاق خام و0.70 Kappa؛ عدم تحقيق أي منهما يتطلب معايرة rubric وتحكيمًا قبل تفسير pass rate.
- يحتفظ بسجل الحكم الأصلي؛ لا يستبدل بالحكم المحكّم بصمت.
- قائد التقييم يدير التحكيم، ومسؤول الإصدار وحده يعتمد قرار GO/NO-GO.
- لا تحسب unknown نجاحًا؛ تعرض نسبة unknown بشكل مستقل.

## 9. حالات الفشل الإلزامية قبل قبول Pilot

1. **نجاح أساسي:** اتصال حقيقي، كتابة artifact صغير، ثم فحصه بأمر داخل Docker وإرفاق دليل النتيجة.
2. **Timeout:** إيقاف الأمر والحاوية، وتسجيل timeout، وعدم احتسابه نجاحًا.
3. **Invalid output:** رفض JSON نهائي غير صالح وتسجيل `invalid_final_json` أو الخطأ المطابق؛ دون إنشاء نجاح جودة.
4. **ملف غير مسموح:** رفض المسار المطلق و`../` ومحاولة الكتابة في fixture أو `SKILL.md`.
5. **Docker أو الصورة غير موجودة:** تسجيل `blocked`؛ عدم تنفيذ الأمر على المضيف كبديل.
6. **ميزانية أو تسعير مفقود:** وقف التشغيل قبل استدعاء المزود عندما يكون حد التكلفة إلزاميًا.
7. **تلف الملفات:** كشف تعديل أي ملف fixture أو مهارة محمية وإيقاف Pilot.
8. **تسريب السر:** فحص تقارير التشغيل والبيئة والمخرجات؛ أي ظهور للسر NO-GO فوري.

